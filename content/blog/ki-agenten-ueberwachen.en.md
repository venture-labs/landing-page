  - type: "paragraph"
    text: "Companies that use AI agents need monitoring that sees failures before anyone notices them in daily work. The risk is rarely a loud crash. Usually an agent simply stops working and nobody notices because no error message appears. Useful monitoring answers three questions: is the agent still running? If not, why? And who is told, and in what form?"
  - type: "heading"
    text: "Why AI agents fail silently"
  - type: "paragraph"
    text: "Classic software often fails visibly: the page does not load, a window shows an error. An agent, by contrast, runs in the background, at night or on a schedule. When it stops, nothing changes for users at first. Things just stop arriving: no summary in the morning, no sorted receipts, no prepared drafts. This often only becomes clear when someone needs the result."
  - type: "paragraph"
    text: "Then there are quiet errors, where the agent runs but delivers something wrong or too little, for example because a login has expired, an interface has changed or a model does not respond. A green tick in the log then only says that something was started, not that anything useful came out."
  - type: "heading"
    text: "What monitoring needs to do"
  - type: "paragraph"
    text: "Checking whether a program is running is not enough. Three building blocks have proven useful."
  - type: "paragraph"
    text: "First, a heartbeat: each agent reports at fixed intervals that it is alive and when it last delivered something. If the report is missing, that is itself the signal. What matters is measuring the outcome rather than the start: did the expected work arrive?"
  - type: "paragraph"
    text: "Second, error classes: not every error needs the same reaction. A brief hiccup, where an external service fails to answer once, often resolves itself on retry. An expired login needs someone to renew it. A bug in the program needs someone to fix it. And some cases need a decision that no agent should make. Knowing the class tells what happens next."
  - type: "paragraph"
    text: "Third, clear responsibility: every alert goes to a place that can act, not to everyone. An alert nobody handles is as good as none."
  - type: "paragraph"
    text: "The form of the alert matters too. An urgent failure belongs with a person at once, minor irregularities are better bundled into one overview in the morning. Reporting every small thing individually creates alarm fatigue, and that makes the important alert get lost. An alert should also say what to do: not just “agent X has failed”, but what failed, since when and what happens next."
  - type: "heading"
    text: "An example from our own operation"
  - type: "paragraph"
    text: "In our own operation several agents run at once, so there is a dedicated monitor. An agent that hits an error reports it with a class: brief hiccup, login or setting, bug in the program, or decision needed. For a bug in the program, the system itself starts a repair run. Anything that needs a decision or a login goes to a person as a question."  # prüfen: Own operation, status 08.11.2026 per the idea list “cluster monitor” (error classes, repair run for code bugs); Christian confirms statement and status date, no agent or system names; number of agents deliberately not stated
  - type: "paragraph"
    text: "Before an alert there is also a retry: temporary errors at external services are tried again first, before anyone is disturbed. That keeps the number of alerts small and attention free for the important ones."  # prüfen: Own operation: retry before reporting per the cluster's operating rules, status 09.11.2026; Christian decides whether this paragraph should be public in this form
  - type: "heading"
    text: "At night: autonomy with a frame"
  - type: "paragraph"
    text: "Many tasks run at night because nobody is waiting. That makes monitoring more important, not less. A frame helps: if agents keep working at night, it is only with an explicit approval for exactly that night, not because the clock shows a certain time. Without approval, daytime rules apply. A load control starts new work only when the machine has headroom."
  - type: "paragraph"
    text: "In our own operation exactly this applies. Autonomy for agents is a decision with a frame: when, how much, and who may say no."  # prüfen: Own operation, status 08.11.2026 per the idea list “The night shift of my AI agents” (approval per night, daytime rules without approval, load control); Christian confirms this is the current state and releases the story
  - type: "heading"
    text: "Limits of any monitoring"
  - type: "paragraph"
    text: "Monitoring does not replace good design. It can only report what it has been taught to measure. Monitoring that never raises a false alarm is as suspicious as monitoring that alarms constantly: in the first case something is probably being missed, in the second nobody listens soon. It helps to collect false alarms and improve the rules from them."
  - type: "paragraph"
    text: "Measurement also needs a cross-check. That something counts as finished does not mean it reaches the user. Checks should therefore look at the outcome: is the evaluation there? Does the live system have the expected version? And there remains a decision about which errors a person must see and which may be handled automatically."
  - type: "heading"
    text: "What companies can do now"
  - type: "paragraph"
    text: "The start is a simple list: which agents run, what should each deliver by when, and who is responsible if it does not? That shows where a heartbeat is needed and which errors deserve which reaction. Where an agent also has an effect on the outside, an approval belongs in front of that effect. The Pulse Check shows what this could look like for a first use case."

    text: "Why does an AI agent need monitoring at all? Because agents mostly work in the background and make no noise when they fail. Without monitoring, a silent failure only shows when someone needs the result."
