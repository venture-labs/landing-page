  - type: "paragraph"
    text: "Wer KI-Agenten im Unternehmen einsetzt, braucht eine Überwachung, die Ausfälle sieht, bevor sie jemand im Tagesgeschäft bemerkt. Das Risiko ist selten ein lauter Absturz. Meist arbeitet ein Agent einfach nicht mehr, und niemand merkt es, weil keine Fehlermeldung kommt. Eine brauchbare Überwachung beantwortet drei Fragen: Läuft der Agent noch? Wenn nicht, woran liegt es? Und wer erfährt es, in welcher Form?"
  - type: "heading"
    text: "Warum KI-Agenten still ausfallen"
  - type: "paragraph"
    text: "Eine klassische Software fällt oft sichtbar aus: Die Seite lädt nicht, ein Fenster zeigt einen Fehler. Ein Agent dagegen läuft im Hintergrund, nachts oder nach einem Zeitplan. Hört er auf zu arbeiten, ändert sich für die Nutzer zunächst nichts. Es kommt nur nichts mehr an: keine Zusammenfassung am Morgen, keine sortierten Belege, keine vorbereiteten Entwürfe. Das fällt oft erst auf, wenn jemand das Ergebnis braucht."
  - type: "paragraph"
    text: "Hinzu kommen leise Fehler, bei denen der Agent zwar läuft, aber Falsches oder zu wenig liefert, etwa weil ein Zugang abgelaufen ist, eine Schnittstelle sich geändert hat oder ein Modell nicht antwortet. Ein grüner Haken im Protokoll sagt dann nur, dass etwas gestartet wurde, nicht, dass etwas Brauchbares herauskam."
  - type: "heading"
    text: "Was eine Überwachung können muss"
  - type: "paragraph"
    text: "Es genügt nicht, nur zu prüfen, ob ein Programm läuft. Drei Bausteine haben sich als sinnvoll erwiesen."
  - type: "paragraph"
    text: "Erstens ein Herzschlag: Jeder Agent meldet in festen Abständen, dass er lebt und wann er zuletzt etwas geliefert hat. Bleibt die Meldung aus, ist das selbst das Signal. Wichtig ist, dass am Ergebnis gemessen wird und nicht am Start: Entscheidend ist, ob die erwartete Arbeit angekommen ist."
  - type: "paragraph"
    text: "Zweitens Fehlerklassen: Nicht jeder Fehler braucht dieselbe Reaktion. Ein kurzer Aussetzer, bei dem ein Fremddienst einmal nicht antwortet, erledigt sich oft von selbst, wenn der Versuch wiederholt wird. Ein abgelaufener Login braucht jemanden, der ihn erneuert. Ein Fehler im Programm braucht jemanden, der es repariert. Und manche Fälle brauchen eine Entscheidung, die kein Agent treffen soll. Wer die Klasse kennt, weiß, was als Nächstes passiert."
  - type: "paragraph"
    text: "Drittens eine klare Zuständigkeit: Jede Meldung geht an eine Stelle, die handeln kann, und nicht an alle. Eine Meldung, die niemand bearbeitet, ist so gut wie keine."
  - type: "paragraph"
    text: "Auch die Form der Meldung zählt. Eine dringende Störung gehört sofort an eine Person, kleinere Auffälligkeiten besser in eine gebündelte Übersicht am Morgen. Wer jede Kleinigkeit einzeln meldet, erzeugt Alarmmüdigkeit, und die führt dazu, dass die wichtige Meldung untergeht. Zur Meldung gehört außerdem, was zu tun ist: nicht nur «Agent X ist ausgefallen», sondern was ausgefallen ist, seit wann und was als Nächstes vorgesehen ist."
  - type: "heading"
    text: "Beispiel aus unserem Betrieb"
  - type: "paragraph"
    text: "In unserem eigenen Betrieb laufen mehrere Agenten gleichzeitig, deshalb gibt es einen eigenen Überwacher. Ein Agent, der einen Fehler hat, meldet ihn mit einer Klasse: kurzer Aussetzer, Login oder Einstellung, Fehler im Programm oder Entscheidung nötig. Bei einem Fehler im Programm startet der Betrieb selbst einen Reparaturlauf.   - type: "heading"
    text: "Nachts: Autonomie mit Rahmen"
  - type: "paragraph"
    text: "Viele Aufgaben laufen nachts, weil dann niemand wartet. Das macht die Überwachung wichtiger, nicht überflüssig. Ein Rahmen hilft: Laufen Agenten nachts weiter, dann nur mit einer ausdrücklichen Freigabe für genau diese Nacht und nicht, weil die Uhr eine bestimmte Zeit zeigt. Ohne Freigabe gelten die Tagesregeln. Eine Lastregelung startet neue Arbeit nur, wenn der Rechner Luft hat."

    text: "In unserem eigenen Betrieb gilt genau das.   - type: "heading"
    text: "Grenzen jeder Überwachung"
  - type: "paragraph"
    text: "Überwachung ersetzt keine gute Konstruktion. Sie kann nur melden, was sie zu messen gelernt hat. Eine Überwachung, die nie falsch alarmiert, ist ebenso verdächtig wie eine, die ständig alarmiert: Im ersten Fall wird vermutlich etwas übersehen, im zweiten hört bald niemand mehr hin. Sinnvoll ist, Fehlalarme zu sammeln und die Regeln daraus zu verbessern."
  - type: "paragraph"
    text: "Auch die Messung braucht eine Gegenprobe. Dass etwas als fertig gilt, heißt noch nicht, dass es beim Nutzer ankommt. Geprüft werden sollte deshalb am Ergebnis: Ist die Auswertung da? Stimmt der Stand auf dem laufenden System? Und es bleibt eine Entscheidung, welche Fehler ein Mensch sehen muss und welche automatisch erledigt werden dürfen."
  - type: "heading"
    text: "Was Unternehmen jetzt tun können"
  - type: "paragraph"
    text: "Am Anfang steht eine einfache Liste: Welche Agenten laufen, was sollen sie bis wann liefern, und wer ist zuständig, wenn das ausbleibt? Daraus ergibt sich, wo ein Herzschlag nötig ist und welche Fehler welche Reaktion verdienen. Wo ein Agent auch Außenwirkung hat, gehört eine Freigabe vor die Wirkung. Wie das für den ersten Anwendungsfall aussehen kann, zeigt der Pulse Check."

  - type: "paragraph"
    text: "Warum braucht ein KI-Agent überhaupt eine Überwachung? Weil Agenten meist im Hintergrund arbeiten und bei einem Ausfall keinen Lärm machen. Ohne Überwachung fällt ein stiller Ausfall erst auf, wenn jemand das Ergebnis braucht."
  - type: "paragraph"
    text: "Was ist ein Herzschlag bei KI-Agenten? Ein regelmäßiges Lebenszeichen: Der Agent meldet, dass er läuft und wann er zuletzt etwas geliefert hat. Bleibt die Meldung aus, löst das den Alarm aus, auch wenn kein Fehler ausdrücklich gemeldet wurde."
  - type: "paragraph"
    text: "Wer wird informiert, wenn ein Agent ausfällt? Das hängt von der Fehlerklasse ab. Vorübergehende Aussetzer werden erst wiederholt, Logins und Entscheidungen gehen an eine zuständige Person, Fehler im Programm an die Stelle, die es repariert. Wichtig ist, dass jede Meldung eine klare Adresse hat."
