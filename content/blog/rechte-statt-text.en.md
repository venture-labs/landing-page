  - type: "paragraph"
    text: "A new starting prompt brings not a single enforced rule with it. If an AI agent is started with new text only, it has everything the last one had, plus a request. An agent is only effectively secured when it starts with adjusted permissions: only the folders, only the tools, only the key the task needs, and a human approval before anything that goes outside. That is what guardrails really are: locks instead of requests."
  - type: "heading"
    text: "What a text can do and what it cannot"
  - type: "paragraph"
    text: "A text in the prompt, whether playbook, role or system instruction, acts on what an agent wants to do. It does not act on what an agent can do. If it says «never write to the customer folder», an agent will follow that in most cases. In the remaining cases it is not the text that decides but whether the folder is writable for it at all."
  - type: "paragraph"
    text: "This is not a flaw of individual models but the nature of text: it is read, weighed and balanced against other instructions. A lock in the system is not weighed. It holds."
  - type: "link"
    text: "The terms behind it in the glossary: AI guardrails"

  - type: "heading"
    text: "What permissions are in concrete terms"
  - type: "paragraph"
    text: "In a company's daily work, permissions are five fairly tangible things. First, a folder of its own in which the agent may read or write, and no other. Second, a list of tools available to it; what is not on the list does not exist for it. Third, a separate key with its own budget, so that misbehavior stays limited and can be assigned to a task. Fourth, a log in which every action appears. Fifth, a human approval before anything that goes outside: to a customer, a payment, a publication or a live system."  # prüfen: Check the list against the vetted landing page ki-agenten-unternehmen (approval before effect, cost cap, log)
  - type: "heading"
    text: "A case: the tool that was missing"
  - type: "paragraph"
    text: "Our own operation includes an agent that looks after customer installations. On November 6, 2026 it was supposed to release a new version of the software and could not, because it simply had no «release version» tool. A sentence in the prompt such as «everything is allowed» would not have changed that. The solution was not a new sentence but the missing tool, with a log line for every release."  # prüfen: Task T257, state 09.11.2026 12:04: done, role sentence in the role file, check exists; verify the wording «the solution was» against the state at go-live; Christian approves the story
  - type: "paragraph"
    text: "The case shows the other side of the same coin: permissions do not only block, they also enable. An agent without the right tool is not careful, it is stuck. Anyone using permissions instead of text decides deliberately which tool belongs to which task with which approval."
  - type: "heading"
    text: "A second case: when the text is right and the format is not"
  - type: "paragraph"
    text: "A reviewing agent once briefly ran on another model with the same instruction. The new model wrote its verdict with asterisks, the downstream parser expected it without. An approval turned into «human needed» because of a one-line format difference. The example shows why even a well-written text is no safeguard: it relies on whatever the model makes of it at the moment. A check that queries the format strictly, and a test after every model switch, secure that."  # prüfen: Case is in the Dev Manager history file (14.10.2026) as one of nine empty review reports; the other causes were an outdated base branch and four real stops.   - type: "heading"
    text: "Why the extra effort pays off"
  - type: "paragraph"
    text: "Permissions cost setup: cutting folders, releasing tools, managing keys, reading logs. In return, the question after an incident changes. Instead of «why did the agent not stick to it?» it becomes «which permission would have prevented that?». The second question has an answer that can be fixed."
  - type: "paragraph"
    text: "Proportion matters. Not every task needs an own agent with its own key. For knowledge and procedures a playbook is enough. Permissions pay off where a mistake goes outside or gets expensive."

  - type: "heading"
    text: "Five steps to secure an agent"
  - type: "paragraph"
    text: "First: write down the worst this agent could do. Second: give it only the folder and tools needed for the task, read access at first. Third: put everything that goes outside behind a human approval. Fourth: set up a cost cap and a log. Fifth: run ten real cases and read each result before the agent may do more."
  - type: "heading"
    text: "Frequently asked questions"
  - type: "paragraph"
    text: "Are clear instructions in the prompt not enough? For knowledge, procedure and tone, yes. For anything that goes outside or costs money, no, because a text enforces nothing."
  - type: "paragraph"
    text: "What does human in the loop mean in this context? That a human approves an action before it takes effect. The approval is a permission in the system, not a sentence in the prompt."
